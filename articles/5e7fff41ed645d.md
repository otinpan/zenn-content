## はじめに
### Crackmes.oneとは
Crackmeとは、リバースエンジニアリングの技術を練習するために作られたプログラムのことです。一般的なCrackmeには、パスワードやシリアルキーの入力を求める認証処理が組み込まれています。例えば、実行すると次のように表示されます。
```
Enter password: ********
Wrong password!
```
解析者はソースコードを見ずに、実行ファイルを解析して正しいパスワードや認証アルゴリズムを特定します。  
[Crackmes.one](https://crackmes.one/)とは、CrackmeをダウンロードできるWebサイトです。

### なぜやるのか
Crackme問題を解くには、実行ファイルを基に、PE解析、静的解析、動的解析、アセンブリ解析、アルゴリズム解析のような技術を使用する必要があります。このように、実行ファイルなどを解析し、内部の構造や動作を調べることを**リバースエンジニアリング**と呼びます。リバースエンジニアリングを学ぶことで、
* 脆弱性分析
* セキュリティコードの開発
* バグ修正
* アセンブリの理解

といった、セキュリティとハッキングの分野に関わる能力の向上が見込まれます。あと、何といっても、リバースエンジニアリングで問題を特定することは、探偵みたいでかっこいいです。

## 準備
環境
* アーキテクチャ: x86-64
* ホストマシン: Windows11 Home
* 仮想マシン: Windows11 Pro

本記事では、Oracle VirtualBox上に構築したWindows 11仮想マシンを使用し、x64dbgによる解析を行います。

仮想マシンを使用する理由は、解析対象の実行ファイルをホストOSから隔離し、セキュリティ上のリスクを低減するためです。また、スナップショット機能を利用することで、解析中に問題が発生しても環境を元の状態に復元できます。

なお、仮想マシンによる隔離は完全な安全性を保証するものではありません。

仮想マシンの環境構築については[VirtualBox 7.0.10 に Windows 11 仮想マシンをインストールする方法](https://qiita.com/mmake/items/711c466431ca73faf2ba)を参考にしてください。なお、デフォルトでHyper-Vが起動している場合、VirtualBoxが非常に重くなることがあります。この場合は、Hyper-Vを停止して、VirtualBoxを使用することで解決できます。

次に以下のツールを仮想マシン上にインストールします。
* [Ghidra](https://github.com/nationalsecurityagency/ghidra): 静的解析ツール
* [x64dbg](https://x64dbg.com/): デバッガ
* [DetectItEasy](https://www.detectiteasy.com/ja/): パッキング判定


## 問題
準備が出来たので、問題をダウンロードしていきます。Crackmes.oneから[search](https://crackmes.one/search)に移動しましょう。今回はDifficultyが2.0の[CrackNotMe's CrackmesForBeginners (CFB) #2](https://crackmes.one/crackme/6a15496417539b5175d12386)を解きます。ここからDownloadで実行ファイルをダウンロードしましょう。  
実行してみましょう。
![](/images/CBF2.png)

```
[*] Enter your solution path (using W/A/S/D):
[+] Key: 
```
と出てくるので、適当に入力してみると
```
[-] Hit a wall at step 7! (x: 3, y: 2)
[-] ACCESS DENIED!
```
と出てきました。この問題では、目的地までのパスを入力することが目的とわかります。

## 解法
### 事前調査
まずは実行ファイルの事前調査をするために、Detect It Easy (DIE) を使用します。
![](/images/DetectItEasy.png)

* ファイル形式: PE64
* アーキテクチャ: x64
* コンパイラ: Visual C/C++
* パッカー: なし(?)
* ImageBase: 0x0000000140000000
* EntryPoint: 0x000000014000949C

実行ファイルの情報が何となくわかりました。これらの情報から、32bitか64bitか、パッキングの有無などを確認できます。特に、パッキングの有無を調べることで、逆アセンブルによる解析をそのまま進められるか、アンパックなどの前処理が必要になるかを判断する手掛かりとなります。

### 動的解析
デバッガを使用して解くこともできます。x64dbgを起動して、実行ファイルを開きます。
実行(f9)で実行、ステップイン(f7)でステップ実行が出来ます。  
まず出来ることは、現在表示されている文字列をメモリから見つけ出すことです。ここでは、パスを入力したときに現れた"Hit a wall ..."を探します。右クリック -> 検索 -> 全てのモジュール -> 文字列検索から"Hit"と入力しましょう。すると下図のように0x7FF642C9677D番地に"Hit ..."という文字列を参照する命令が見つかるので、ここら辺からトレースしましょう。

![](/images/CBF_Hit.png)

どうやら、入力文字がW/A/S/Dのどれに該当するかを判定して、ループを回しているっぽいです。適当な場所にブレークポイントを置いて、そこまで実行して、メモリの情報を取りましょう。
```
00007FF642C96620 | 48:8D45 C8               | lea rax,qword ptr ss:[rbp-38]           |
00007FF642C96624 | 48:837D E0 0F            | cmp qword ptr ss:[rbp-20],F             |
00007FF642C96629 | 48:0F4745 C8             | cmova rax,qword ptr ss:[rbp-38]         |
00007FF642C9662E | 42:0FB60C38              | movzx ecx,byte ptr ds:[rax+r15]         | rax+r15*1:"DDSDDWD"
```
ここら辺にブレークポイントを置きましょう。何回か回すといろいろなことが分かります。
* rbp-38: 入力文字列 (例 SSDDSDDWD)
* rbp-28: 入力文字列の長さ (例 9)
* r15: 現在処理している入力文字のインデックス（0始まり） (例 2回目のループ -> 1)
* (esi,edi): (i,j)

## まとめ
DIEを使用して、実行ファイルの情報を調べた後、Ghidraやx64dbgなどの解析ツールを使用して、Crackmes.oneの問題を解いてみました。静的解析・動的解析のいずれでも、アセンブリから元のソースコードを推測することが解決のカギになったと思います。リバースエンジニアリングでは、問題の範囲を特定する推察力、アセンブリやAPIの知識、普段のコーディング経験等の、さながら総合格闘技のような、広範囲の能力が試されます。リバースエンジニアリングで養われる直感や低レイヤの知識は、AIが台頭する将来も役に立つと信じています。
