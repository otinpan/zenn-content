# はじめに
## なぜやるか
ここ数か月、個人で[KaniVolcanoEngine](https://github.com/otinpan/KaniVolcano)というRust/ECS/Vulkan製のゲームエンジンを作成していました([記事](https://zenn.dev/otinpan/articles/a2215fcf315987))。また、同時にリバースエンジニアリングについても勉強していました。その理由は、**リバースエンジニアリングとゲームエンジンでゲームのリメイクの手助けをしたい**という考えがあったからです。

リバースエンジニアリングで高級言語に翻訳し、それをLLMに食わせてロジックを解釈、自然言語の仕様書からゲームエンジンのAPIに落とし込む。というような流れで、ゲームのリメイクの負担を減らしたり、ブラッシュアップするというアイデアがありました。

これは、ソースコードがすでに無くなっていたり、手に入らない場合にも有用です。そこで障壁となっていたのが、実行ファイルからロジックを解析するという部分です。なんとなく、実行ファイル -> アセンブリ -> 高級言語 -> LLM解釈 -> 仕様書という流れでやろうと思っていましたが、[REA](https://github.com/morluto/rea)というものが出てきました。REAはCodexやClaudeのようなAIエージェントと[Ghidra](https://github.com/nationalsecurityagency/ghidra)というリバースエンジニアリングフレームワークをつなぐオープンソースのツールです。これを使用することで、実行ファイルをLLMがGhidraで解析し、中身がどうなっているかを調べることが出来ます。

ゲームに適用すると、ゲームの実行ファイルからゲームのロジックを読み取り、それをもとにゲームの仕様書を作成することが出来ます。すると、ゲームの外部から観測できる振る舞いだけでなく、その振る舞いを生み出す内部のロジックまで再現することが出来るのです。

## ゲーム再構築の2つのアプローチ
すぐに想像できる範囲では、ゲームを実行ファイルから再構築するアプローチは2つあります。
* ゲームをプレイ -> プレイヤーが画面の情報を観測 -> 内部ロジック推測 -> 仕様書
* 実行ファイル -> リバースエンジニアリング -> 内部ロジック復元・推定 -> 仕様書

前者は一般にブラックボックス解析、後者は内部情報を利用するホワイトボックス寄りの解析になります。ただ、後者のアプローチの方がより正確に再現できます。

例えば、青鬼がプレイヤーを追跡する場面を考えます。
前者のプレイによる観測では、「青鬼はプレイヤーを発見すると追いかけてくる」という仕様は推測できますが、以下のことは簡単にはわかりません。

* 追跡開始条件
* 障害物をどのように回避するか
* 追跡速度
* 追跡終了条件
* 衝突判定の範囲

また、後者のアプローチでは観測していないイベントも調査できる可能性があります。例えば、「特定の部屋に入ったときにあるアイテムを所持していたら、隠しイベントが発生する」というような隠し条件は前者のゲームプレイに基づくアプローチでは、簡単に発見できるとは限りません。

ただ、後者のアプローチでも弱点があります。例えば、解析できないライブラリや外部データが存在したりすると、実際のロジックと推測が食い違います。

## 方法
まず、実行ファイルを手に入れます。REAに実行ファイルを渡し、Ghidraで解析してもらいます。その後、仕様書を作成してもらいます。その仕様書をLLMに読み込ませ、KaniVolcanoEngineのAPIで実装するように指示します。待っていたら完成します。

### 2Dシューティングゲーム
[raylib](https://www.raylib.com/)とC++で実装したシューティングゲームを作りました。この実行ファイルをREA経由でLLMに解析してもらい、要件仕様書を書いてもらいます。

## 2. ゲーム概要

プレイヤーがWASDで移動し、マウスで照準を合わせて敵を撃つ、見下ろし型の2Dシューティングゲーム。フィールドにはプレイヤー1体、敵5体、障害物8個を配置する。敵はランダムに移動しながらプレイヤーへ射撃する。

プレイヤーが生存したまま敵を全滅させれば勝利、プレイヤーのHPが0になれば敗北となる。結果画面からRキーで同じシードのゲームを再開できる。

## 4. オブジェクトと基本パラメータ

| 種類 | 初期数 | HP | 当たり判定・描画寸法 | 通常速度 |
|---|---:|---:|---|---:|
| プレイヤー | 1 | 5 | 32×32 | 250 |
| 敵 | 5 | 3 | 32×32 | 100 |
| 障害物 | 8 | HP処理なし | ランダム幅55～115、高さ45～85 | 静止 |
| プレイヤー弾 | 発射ごとに生成 | HP処理なし | 8×8 | 400 |
| 敵弾 | 発射ごとに生成 | HP処理なし | 8×8 | 400 |

当たり判定は軸平行矩形（AABB）であり、キャラクターの見た目の回転に追従して回転しない。寸法は全幅・全高で、位置から半幅・半高さを引いて矩形左上を得る。

障害物は弾を遮り、HealthComponentを持たないため命中によるHP減少・破壊は生じない。

## 5. 入力とプレイヤー操作

| 入力 | 操作 |
|---|---|
| W / A / S / D | 上 / 左 / 下 / 右へ移動 |
| マウス位置 | プレイヤーの照準方向を指定 |
| マウス左クリック | 射撃要求 |
| マウス左ボタンを押し続け | クールダウンが解消するたびに射撃 |
| R押下 | 結果画面から再開 |

### 5.1 移動ベクトル

入力ベクトルを `u=(D−A, S−W)` とする。各キーの値は押下中1、それ以外0。

```text
uがゼロ: velocity = (0, 0)
それ以外: velocity = normalize(u) * 250
```

正反対のキーは相殺される。斜め移動でも速度の大きさは250を維持する。

### 5.2 照準

固定更新の入力反映段階で、移動前のプレイヤー中心からマウス位置への差分を計算する。

```text
delta = mousePosition - playerPosition
if dot(delta, delta) > 0.0001:
    rotation = atan2(delta.y, delta.x) * 57.295776
```

差分が閾値以下なら直前の角度を保持する。初期角度は0度。射撃要求の方向には保持した角度のcos/sinを使うため、マウスが中心と同じ位置でも直前の向きに射撃できる。

### 5.3 入力保持

入力は描画ループごとに取得し、固定更新で利用する。

- 移動ベクトル、マウス位置、ボタンの押し続け状態は最新値へ置き換える。
- クリック発生とR押下は未消費フラグとORして保持する。
- 固定更新がない描画ループで検出したクリックも、次の固定更新まで残る。
- フラグは真偽値であり、複数回のクリックを回数として蓄積しない。
- 固定更新末尾でクリック・Rのイベントフラグをクリアする。

保持したクリックは射撃要求として1回利用される。クールダウン中のクリックを、発射可能になるまで予約し続ける仕組みではない。

## 6. 敵AI

### 6.1 ランダム移動

各敵は方向変更タイマーを持つ。初期値は0。

1. 固定更新でタイマーからdtを引く。
2. 0以下なら角度θを0～2πの一様乱数から選ぶ。
3. 速度を `(cosθ, sinθ) * 100` に設定する。
4. 次の変更までの時間を0.5～2.0秒の一様乱数から選ぶ。

最初の固定更新で方向を決める。障害物で移動できなくなっても、移動衝突処理自体は方向変更タイマーを再設定しない。方向変更はタイマーの条件に従う。

### 6.2 射撃

各敵の初回射撃待ち時間は生成時に0.4～1.5秒からランダムに設定する。発射後は1.5秒固定で待つ。

射撃処理時に活動中のプレイヤーへの差分を求める。差分の長さの二乗が0.0001を超え、待ち時間が0なら弾を生成する。発射済みの弾は一定方向へ進み、プレイヤーを追尾しない。

### 6.3 更新順序

敵のComponentは以下の数値優先度で昇順に更新する。

| 優先度 | 処理 |
|---:|---|
| 5 | EnemyAI：方向変更の判断と速度設定 |
| 10 | Move：座標移動と衝突処理 |
| 20 | Shooting：照準と射撃 |

したがって、敵は移動後の座標から射撃する。同じ優先度のComponentは登録順を保持する。

## 7. 射撃とダメージ

| 項目 | プレイヤー | 敵 |
|---|---|---|
| 初回待ち時間 | 0 | 0.4～1.5秒の乱数 |
| 発射後クールダウン | 0.2秒 | 1.5秒 |
| 発射位置 | 発射処理時のActor中心 | 同左 |
| 弾速 | 400 | 400 |
| ダメージ | 1 | 1 |

射撃処理では先に `cooldown=max(0,cooldown−dt)` とし、その後で要求と方向を検査する。発射した場合にクールダウンを上表の値へ設定する。残時間を保持したまま複数発を一括生成する方式ではないため、実際の発射間隔は固定更新と浮動小数点演算の影響を受ける。

弾生成時に方向を正規化し、400倍した速度を保存する。キャラクターの速度は弾へ加算しない。

被弾時はHPから非負のダメージを引き、HPの下限を0とする。敵は通常3発、プレイヤーは通常5発の命中でHPが0になる。

## 8. 移動と衝突

### 8.1 キャラクター移動

移動量 `(dx,dy)=velocity*dt` に対して、次の小ステップ数を求める。

```text
n = max(1, ceil(max(abs(dx), abs(dy)) / 4))
```

各小ステップでXを `dx/n`、次にYを `dy/n` 移動させ、それぞれの候補位置を独立に検査する。移動できる軸だけ採用するため、斜めに障害物へ当たると面に沿って滑る。

移動を遮るのはフィールド境界と障害物のみ。敵同士、敵とプレイヤーは互いを押し返さない。障害物との矩形検査は面積のある重なりを拒否し、辺が触れるだけなら移動可能。

### 8.2 弾の衝突対象

| 弾 | プレイヤー | 敵 | 障害物 | 弾 |
|---|---|---|---|---|
| プレイヤー弾 | 対象外 | 命中 | 命中 | 対象外 |
| 敵弾 | 命中 | 対象外 | 命中 | 対象外 |

対象Actorは活動状態である必要がある。

### 8.3 弾の連続衝突判定

弾は旧中心から新中心への移動区間全体を検査する。

1. 対象AABBを弾の半幅・半高さ（各4）だけ外側へ拡張する。
2. 弾中心の線分と拡張矩形について、X/Yそれぞれの侵入・退出パラメータを求める。
3. 両軸に共通する区間が `t∈[0,1]` にあれば命中候補とする。
4. 移動差の絶対値が1e-6未満の軸は平行として、開始座標が範囲内か検査する。
5. 最小の侵入tを持つ対象を1つ選び、弾中心をその衝突位置へ戻す。
6. 対象がHPを持つ場合にダメージを与え、弾を破棄状態にする。

複数の対象に同じtで命中する場合は、Colliderリストで先の対象を維持する。通常の生成順では障害物が敵より先のため、プレイヤー弾の障害物・敵への同時命中では障害物が選ばれる。

この検査は弾の移動線分と、検査時点の対象矩形との判定である。全Actorの動きを同時に解く物理シミュレーションではない。

### 8.4 画面外の弾

命中しなかった弾は、新中心が以下のいずれかを満たすと破棄状態になる。

```text
x < -8  または x > 1288
y < -8  または y > 728
```

等号では残る。外側余白は弾の半幅ではなく全幅・全高の8。弾はキャラクターと異なり、HUDとの境界Y=48では制限されない。

## 9. 初期配置と乱数

### 9.1 初期化順序

プレイヤーを中心(640,360)に生成し、障害物8個、敵5体の順で配置する。障害物・敵の候補選択にはGameが持つ共通の乱数生成器を使用する。

### 9.2 乱数

既定シードは12345。起動引数で変更できる。

```powershell
.\game.exe --seed 42
```

シードは十進数字のみの32ビット符号なし整数（0～4294967295）。空文字、符号、不正文字、桁あふれは拒否する。乱数生成器はMT19937相当の状態更新・初期化定数を持つ実装として読み取れる。

実数乱数は概ね `float(uint32Random * 2^-32 * (max−min)) + min` の変換で得る。本書の乱数範囲は名目上の上下限を記載しており、float丸めにより上端値になる可能性を含む。

### 9.3 安全領域

プレイヤー中心の周囲に、左上(530,250)、幅220、高さ220の正方形を確保する。右下は(750,470)。障害物・敵の候補矩形がこの領域と重なる場合は拒否する。辺の接触だけなら拒否しない。

### 9.4 障害物のランダム配置

| 項目 | 候補値・条件 |
|---|---|
| 幅w | 55～115 |
| 高さh | 45～85 |
| 中心X | `24+w/2` ～ `1256−w/2` |
| 中心Y | `72+h/2` ～ `696−h/2` |
| 安全領域 | 候補の実寸矩形と重ならないこと |
| 既存Colliderとの間隔 | 候補を四辺30ずつ拡張した矩形が、既存の全Colliderと重ならないこと |

### 9.5 敵のランダム配置

| 項目 | 候補値・条件 |
|---|---|
| 中心X | 40～1240 |
| 中心Y | 88～680 |
| 安全領域 | 実寸32×32の矩形と重ならないこと |
| 既存Colliderとの間隔 | 候補を四辺20ずつ拡張した72×72の矩形が、既存の全Colliderと重ならないこと |

既存Colliderにはプレイヤー、配置済み障害物、配置済み敵を含む。初期配置の間隔検査は、ゲーム中の移動衝突の対象条件とは異なる。

### 9.6 配置の打ち切りと固定配置

各オブジェクトについて候補を最大512回試す。1個でも配置できなければ、その試行で生成したActorをプレイヤーも含めて破棄し、全体を最初からやり直す。全体の試行は最大8回。試行間で乱数生成器は巻き戻さない。

8回とも失敗した場合は、次の固定配置を直接生成する。

| 種類 | 中心座標・寸法 |
|---|---|
| プレイヤー | (640,360)、32×32 |
| 障害物 | X={170,470,770,1070}とY={200,520}の全組合せ、計8個。各80×60 |
| 敵 | X={100,360,620,880,1140}、Y=88、計5体 |

## 10. 勝敗・死亡・再開

### 10.1 ゲーム状態

| 値 | 状態 | 挙動 |
|---:|---|---|
| 0 | プレイ中 | Actor更新と勝敗判定を行う |
| 1 | 勝利 | Actor更新を停止し、勝利表示と再開入力を処理する |
| 2 | 敗北 | Actor更新を停止し、敗北表示と再開入力を処理する |

各固定更新のActor処理完了後、次の順で結果を判定する。

1. プレイヤーが存在しない、またはHPが0以下なら敗北。
2. それ以外で敵が全滅していれば勝利。
3. それ以外はプレイ中を継続。

同じ固定更新で双方が全滅した場合は敗北が優先される。

### 10.2 Actorの死亡状態

| Actor状態値 | 意味 | 更新 | 描画 |
|---:|---|---|---|
| 0 | 活動 | 実施 | 実施 |
| 1 | 非活動 | 停止 | 実施 |
| 2 | 破棄対象 | 停止 | 対象外 |

HPが0になったプレイヤーは状態1、敵は状態2になる。敵と消滅した弾は固定更新末尾で実際に破棄する。プレイヤーは敗北画面に残り、再開・終了時に破棄する。

結果確定後は残ったキャラクターと弾の更新を止める一方、描画は継続する。

### 10.3 再開

勝利・敗北中にR押下を受け取った固定更新で、次の処理を行う。

1. Sceneが持つActorを全て破棄する。
2. プレイヤー参照をクリアする。
3. 保存した起動時シードで乱数生成器を再初期化する。
4. ゲーム状態をプレイ中へ戻し、入力をリセットする。
5. 初期配置を再生成する。

同じシードから再生成するため、再開時の初期配置は同じになる。テクスチャはGame内の既存リソースを再利用する。

## 11. 更新・描画ループ

### 11.1 固定更新

更新周期は1/60秒。実時間の蓄積は倍精度、Actorへ渡すdtは単精度の1/60相当値を使用する。

```text
入力を取得・保持
now = 現在時刻
accumulator += min(now - previousTime, 0.25)
previousTime = now

while accumulator >= 1/60:
    固定更新(float(1/60))
    accumulator -= 1/60

現在状態を1回描画
```

通常起動の目標FPSは0で、アプリ側の目標FPSに基づく待機を設けない。描画ループ1回で固定更新が0回または複数回となる。更新間の補間位置を描く処理は確認したメインループにはなく、現在の状態を描く。

経過時間は1ループ最大0.25秒だけ蓄積する。1秒停止しても1秒分を追いつかせず、超過分を捨てる。蓄積済み端数は維持する。実際の描画速度・同期は実行環境に依存する。

### 11.2 Scene内の固定更新順序

1. 更新中フラグを立てる。
2. 活動リストの各Actorへ入力反映処理を行う。
3. 活動リストの各Actorについて、Componentを優先度順に更新し、その後Actor固有の更新を行う。途中で非活動・破棄状態になったActorは以降の更新を止める。
4. 更新中フラグを下ろす。
5. 保留Actorを活動リストへ追加し、保留リストを空にする。
6. 破棄状態のActorを集め、破棄する。
7. Game側で勝敗を判定する。
8. クリック・再開のイベントフラグをクリアする。

生成した弾はその固定更新では移動せず、次の固定更新から動く。Collider自体は生成時に即時登録する。更新後に活動リストへ合流するため、次の移動前に描画されることはある。

## 12. 描画とアセット

### 12.1 描画順序

1. フィールド背景を描く。
2. Sceneの活動リスト順に、破棄状態ではないActorの描画Componentを実行する。
3. 上部HUDを描く。
4. 結果確定時は暗転矩形、結果文字列、再開案内を描く。

### 12.2 キャラクターと弾

プレイヤーと敵は32×32の表示領域を持つ。対応テクスチャがロード済みなら全画像をその領域へ拡縮し、中心を軸に `rotation+90度` で描く。テクスチャがない場合は対応色の軸平行矩形として描く。

キャラクターには中心から向きの先24ピクセルまで、太さ3の白い方向線を描く。障害物と弾は矩形描画で、弾は8×8。弾の当たり判定と見た目はともに回転しない。

### 12.3 リソース管理

テクスチャ読込処理には `assets/textures/player.png` と `assets/textures/enemy.png` のパス構築がある。画像が利用できない場合の矩形描画分岐を持つ。起点ディレクトリの実際の解決結果、画像内容、読込エラー時の全分岐は実行確認していない。

Gameの生成時にリソースを準備し、R再開では保持する。Gameの破棄時にロード済みテクスチャを解放する。

## 13. オブジェクト管理構造

```text
Game / Scene
├─ 活動Actorリスト（所有）
├─ 更新中に生成したActorの保留リスト（所有）
├─ Collider登録リスト（参照）
├─ プレイヤー参照
├─ 乱数生成器・保存シード
└─ キャラクターテクスチャ

Actor
└─ Componentリスト（所有、優先度順）
```

| 操作 | 管理上の処理 |
|---|---|
| Actor生成 | 基底コンストラクタでSceneへ登録。更新中は保留、それ以外は活動リスト |
| Component生成 | 基底コンストラクタで所有Actorへ登録。優先度昇順で挿入 |
| Collider生成 | ActorへのComponent登録に加えてGameのColliderリストへ登録 |
| Collider破棄 | GameのColliderリストから解除 |
| Component破棄 | 所有ActorのComponentリストから解除 |
| Actor破棄 | 所有Componentを破棄し、Sceneの活動・保留リストから解除 |
| Sceneクリア | 活動・保留リストのActorを全て破棄 |

## 14. 起動引数と補助実行モード

```text
game [--seed unsigned_integer] [--smoke-test]
```

不正シードでは `Invalid seed`、未対応引数や値のない`--seed`ではUsageを出力し、終了コード1で終了する。通常終了のコードは0。

`--smoke-test` は補助モードであり、通常プレイと以下が異なる。

- 目標描画FPSを60に設定する。
- 各入力取得で右方向への移動、照準位置(1100,360)、射撃ボタン押下を強制する。
- ループカウンタが120の描画後に `smoke-test.png` の保存を要求する。
- カウンタが180に到達するとループを終了する。

本解析ではこのモードを実行しておらず、画像ファイル生成の成功や所要実時間は未検証。

# おわり
REAを用いてLLMにゲームの静的解析を行わせ、ゲームロジックを再現するための要件仕様書を生成してもらいました。さらに、その仕様書をもとに、LLMが自作ゲームエンジン（KaniVolcanoEngine）のAPIを使用してゲームを実装した結果、元のゲームとかなり近い動作をするゲームを再構築できました。

さらに、再現されたゲームはKaniVolcanoEngineの慣習に沿ったソースコードで実装されていました。(個人的にはここが一番うれしい)

このアプローチは、既存ゲームのリメイクや、ソースコードが失われたゲームの復元、元ゲームのカスタマイズなどに応用できる可能性があると考えています。もちろん、著作権や解析精度など、技術面・権利面の課題も多く、そう簡単な話ではないと思います。

今後は、ゲームの内部構造を調査する**解析エージェント**、解析結果から仕様書を作成・管理する**プロデューサーエージェント**、仕様書に基づいてゲームを構築する**実装エージェント**、そして元ゲームとの違いを検証する**検証エージェント**などが協調する仕組みを開発したいと考えています。

最終的には、各エージェントが解析・実装・検証・修正を繰り返すことで、元ゲームの動作をより高精度に再現したり、ユーザーの要求に応じてゲームをカスタマイズしたりできるようなツールを目指したいです。
