# はじめに

現在、RustとVulkanを用いた自作ゲームエンジン [KaniVolcanoEngine](https://github.com/otinpan/KaniVolcano) を開発しています。
KaniVolcanoEngineでは、Jobの並列実行を実現するために、WindowsのFiber APIを用いたJob Systemを実装しています。
今回、ReleaseビルドでJob Systemを動作させたところ、assertによるpanicや、RefCellの借用エラーが発生しました。原因を調査する過程で、Fiberのスレッド間移動と、コンパイラによるTLS（Thread Local Storage）アクセスの最適化が関係している可能性が浮上しました。
本記事では、Job Systemの構成、発生したバグ、およびコンパイラ最適化とFiberの関係について説明します。

# Job Systemの構成
KaniVolcanoEngineのJob Systemでは、
OSスレッドであるWorkerと、
Jobの実行単位であるFiberを分離して管理しています。

| 用語 | 説明 |
| --- | --- |
| Job | 実行する処理 |
| Worker | Jobを実行するOSスレッド |
| Executor | Workerの実行状態を管理する構造体 |
| Manager Fiber | Workerに固定されたスケジューラー |
| Job Fiber | 独自のスタックを持ち、Jobを実行するFiber |
| JobSystemShared | Worker間で共有するJobやFiberの管理情報 |

構造を簡略化すると以下のようになります。

```text
JobSystemShared
    ├── Job Queue
    ├── Ready Fiber Queue
    └── Free Fiber Queue

WorkerA (OS Thread)
    ├── ExecutorA (TLS)
    └── Manager FiberA

WorkerB (OS Thread)
    ├── ExecutorB (TLS)
    └── Manager FiberB

Job Fiber Pool
    ├── Fiber 0
    ├── Fiber 1
    ├── Fiber 2
    └── ...
```

WorkerとManager Fiberは1対1で対応していますが、Job Fiberは特定のWorkerに固定されていません。

## Executor
各Workerは、自身の実行状態を管理するExecutorを持ちます。

```rust
pub(crate) struct Executor {
    worker_id: WorkerId,
    shared: Arc<JobSystemShared>,

    // Thread-affine:
    // created and destroyed only within this worker.
    manager_fiber: FiberHandle,

    current_fiber: Option<FiberId>,
}
```
* `manager_fiber`
    * Workerに固定されているFiber
    * Job Fiberの選択や実行後の管理を行う
* `current_fiber`
    * 現在実行しているJob FiberのID
    * Job Fiberを実行していない場合は`None`

Executorは、TLS（Thread Local Storage）に保持しています。

```rust
thread_local! {
    static CURRENT_EXECUTOR: RefCell<Option<Executor>>
        = const { RefCell::new(None) };
}
```

TLSは、OSスレッドごとに独立した変数を保持する仕組みです。

例えば、WorkerAとWorkerBが存在する場合、それぞれのExecutorは異なるアドレス (アドレスは例) に存在します。

```text
WorkerA
    CURRENT_EXECUTOR
        Address: 0x1000
        ExecutorA

WorkerB
    CURRENT_EXECUTOR
        Address: 0x2000
        ExecutorB
```

各Workerは、同じ`CURRENT_EXECUTOR`という変数名を使用しても、自身のExecutorにアクセスすることができます。

## Executorへのアクセス

現在のWorkerのExecutorを取得するために、
以下のヘルパー関数を定義しています。

```rust
fn with_current_executor<R>(
    f: impl FnOnce(&mut Executor) -> R
) -> R {
    CURRENT_EXECUTOR.with(|slot| {
        f(
            slot.borrow_mut()
                .as_mut()
                .expect("no current Executor")
        )
    })
}
```

この関数は、現在のWorkerのExecutorを一時的に可変借用し、引数として渡されたクロージャ`f`を実行します。

例えば、Executorの状態を書き換えることができます。

```rust
with_current_executor(|executor| {
    executor.current_fiber = None;
});
```

このようにすることで、Executorへのアクセス処理を共通化し、RefCellの借用を関数の内部で完結させています。

# Job Systemの実行フロー
各Workerでは、以下のループを実行しています。

```rust
impl Executor {
    fn run() -> Result<()> {
        loop {
            let shared = Self::current_shared();

            if shared.is_shutdown() {
                break;
            }

            shared.process_wake_requests();

            if let Some(id) = shared.next_ready_fiber() {
                unsafe {
                    Self::resume_fiber(id);
                }
            } else {
                shared.wait_for_work();
            }
        }

        let executor = CURRENT_EXECUTOR
            .with(|slot| slot.borrow_mut().take())
            .unwrap();

        unsafe {
            executor.manager_fiber.convert_back_to_thread()
        }
    }
}
```

Workerは、共有データである`JobSystemShared`から`next_ready_fiber()`により、実行可能なFiberを取得します。

実行可能なFiberが存在する場合は、`resume_fiber()`を呼び出して実行を開始または再開します。
`resume_fiber()`では、実行するFiberのIDをExecutorの`current_fiber`に設定し、`SwitchToFiber()`を呼び出し、Fiberを切り替えます。

実際のコードを簡略化すると、以下のようになります。

```rust
unsafe fn resume_fiber(id: FiberId) {
    let target = with_current_executor(|executor| {
        assert!(executor.current_fiber.is_none());

        let fiber = executor.shared.fiber(id);

        fiber.prepare_resume();

        executor.current_fiber = Some(id);

        fiber.handle().as_ptr()
    });

    unsafe {
        SwitchToFiber(target);
    }

    with_current_executor(|executor| {
        executor.current_fiber = None;
    });

    // Fiberの待機・完了状態に応じた処理
    // ...
}
```

Job FiberからManager Fiberに実行が戻ると、`SwitchToFiber()`の次の処理から実行が再開され、`current_fiber`に`None`を設定します。

```text
Manager Fiber
    |
    | current_fiber = Some(id)
    |
    | SwitchToFiber(job_fiber)
    v
Job Fiber
    |
    | Jobを実行
    |
    | 
    | return_to_manager()
    | SwitchToFiber(manager_fiber)
    v
Manager Fiber
    |
    | current_fiber = None
    |
    | 次のJob Fiberを選択
```

Jobの実行が完了すると、`return_to_manager()`を呼び出します。
```rust
pub(crate) unsafe fn return_to_manager() {
    let manager = with_current_executor(|executor| {
        assert!(executor.current_fiber.is_some());

        executor.manager_fiber.as_ptr()
    });

    unsafe {
        SwitchToFiber(manager);
    }
}
```

Job Fiberを実行する前には、必ず`current_fiber`にFiber IDを設定しています。
そのため、Job Fiberの実行中には、以下のassertが常に成立するはずです。

```rust
assert!(executor.current_fiber.is_some());
```

なお、Jobの完了時だけでなく、別のJobの完了を待つ場合にもManager Fiberに実行を戻します。


# Fiberのスレッド間移動
Fiberは独自のスタックと実行コンテキストを持っています。そのため、処理の途中で実行を中断し、後から中断した位置から実行を再開することができます。例えば、JobAの中でJobBとJobCを実行し、それらの完了を待つ場合を考えます。

```text
JobA
    |
    | JobB, JobCを登録
    |
    | JobB, JobCの完了を待つ
    |
    | 処理を再開
    |
    | 完了
```

JobAがJobBとJobCの完了を待つ際にWorker全体をブロックしてしまうと、そのWorkerは他のJobを実行することができません。そこで、このWorkerはJobAを実行しているFiberを中断し、Manager Fiberに実行を戻します。
Workerは再度`next_ready_fiber()`を呼び、実行可能なFiberを取得することで、別のJobを実行することができます。

KaniVolcanoEngineでは、実行可能なFiberをWorker間で共有しているキューによって管理しています。
そのため、WorkerAで中断したFiberが、WorkerBで再開されることがあります。
WindowsのFiber APIでは、適切な同期を行うことで、別のスレッドで作成されたFiberを実行することができます。


例えば、以下のような実行フローになります。

```text
WorkerA                        WorkerB

ManagerFiberA                 ManagerFiberB
    |
    | current_fiber = Some(1)
    |
    v
Fiber1
    |
    | Jobを実行
    |
    | Jobの完了待ち
    |
    v
ManagerFiberA
    |
    | current_fiber = None
    |
    | Fiber1を待機状態にする
    |
    | 待機条件が成立
    |
    +---- ReadyFiberQueue --------+
                                    |
                                    v
                                ManagerFiberB
                                    |
                                    | current_fiber = Some(1)
                                    |
                                    v
                                Fiber1
                                    |
                                    | 中断位置から再開
                                    |
                                    | Jobが完了
                                    |
                                    v
                                ManagerFiberB
                                    |
                                    | current_fiber = None
```

このとき、Fiber1のスタックや実行状態は保持されたまま、実行するOSスレッドだけが変化します。
これによって、特定のWorkerに処理が集中することを避け、柔軟な負荷分散を実現しています。

# 発生したバグ
ReleaseビルドでJob Systemを動作させたところ、以下のassertが失敗することがありました。
```rust
assert!(executor.current_fiber.is_some());
```

また、Executorを取得する際に、以下のようなエラーが発生することもありました。
```text
RefCell already borrowed
```

しかし、Job Fiberの実行前には、必ず`current_fiber`にFiber IDを設定しています。
さらに、ExecutorへのアクセスにはTLSを使用しているため、異なるWorkerが同じExecutorにアクセスすることは、通常想定していません。

なぜ、このようなエラーが発生するのでしょうか。


# コンパイラ最適化とTLS
## コンパイラの前提
通常のプログラムでは、ある関数を実行している途中で、その関数を実行するOSスレッドが変化することはありません。

例えば、以下のようなコードを考えます。
```rust
fn example() {
    let before = Executor::current_worker_id();

    some_function();

    let after = Executor::current_worker_id();
}
```

通常であれば、`some_function()`の実行前後で、実行しているOSスレッドは変化しません。そのため、`current_worker_id()`を呼び出す際に参照するTLS領域も同じものになります。
コンパイラは、この性質を利用して、TLSのアドレス計算を省略したり、一度取得したアドレスを再利用したりする可能性があります。

概念的には、以下のような最適化です。
### 最適化前
```rust
let tls_address = get_tls_address();
let before = read_worker_id(tls_address);

some_function();

let tls_address = get_tls_address();
let after = read_worker_id(tls_address);
```

### 最適化後
```rust
let tls_address = get_tls_address();
let before = read_worker_id(tls_address);

some_function();

let after = read_worker_id(tls_address);
```
通常のプログラムでは、同じTLS領域を参照するため、このような最適化を行っても問題ありません。

しかし、Fiberのスレッド間移動が存在する場合は、事情が異なります。

## Fiberのスレッド間移動による問題
例えば、以下のようなコードを考えます。

```rust
fn example() {
    let before = Executor::current_worker_id();

    // Fiberを中断してManager Fiberに戻る
    suspend();

    let after = Executor::current_worker_id();
}
```

WorkerAでFiberを中断し、WorkerBで再開したとします。
この場合、期待する結果は以下のようになります。
```text
before = WorkerA
after  = WorkerB
```

しかし、コンパイラがTLSのアドレスを再利用した場合、以下のようになる可能性があります。
```text
WorkerAで実行
    |
    | TLSアドレスを取得
    | address = 0x1000
    |
    | WorkerAのExecutorを参照
    |
    | Fiberを中断
    |
    v

WorkerBで再開
    |
    | TLSアドレスを再利用
    | address = 0x1000 (本来はWorkerBのTLSから0x2000を取得したい)
    |
    | WorkerAのExecutorを参照 (最適化によってWorkerAのTLSを参照)
```

本来であれば、WorkerBで再開した時点で`0x2000`を取得する必要があります。
しかし、以前取得した`0x1000`がスタックや保存されたレジスタなどに残っていた場合、WorkerBで実行しているにもかかわらず、WorkerAのExecutorにアクセスする可能性があります。


# 発生したバグとの関係
TLSアドレスが再利用されているという仮説によって、今回発生した2種類のエラーを説明することができます。

## current_fiber.is_some()の失敗

正常な実行フローは以下のようになります。

```text
WorkerA
    Fiber1を実行
    current_fiber = Some(1)

    Fiber1を中断
    current_fiber = None

WorkerB
    Fiber1を再開
    current_fiber = Some(1)

    Fiber1のJobが完了
    assert!(current_fiber.is_some())
    current_fiber = None
```

しかし、TLSアドレスが再利用された場合、以下のような状態になる可能性があります。

```text
WorkerA
    ExecutorA (0x1000)
    Fiber1を中断
    current_fiber = None
WorkerB
    ExecutorB (0x2000)
    current_fiber = Some(1)

    Fiber1のJobが完了

    ExecutorA (0x1000)を参照

    assert!(ExecutorA.current_fiber.is_some())
    -> panic
```

WorkerBでFiberを実行しているにもかかわらず、WorkerAのExecutorにアクセスしてしまいます。
WorkerAはすでにManager Fiberに戻っており、`current_fiber`を`None`に設定している場合があります。

その結果、本来成立するはずのassertが失敗します。

## RefCell already borrowed
通常、各Workerは独立したRefCellを持ちます。

```text
WorkerA -> RefCellA -> ExecutorA
WorkerB -> RefCellB -> ExecutorB
```

しかし、TLSアドレスが再利用されると、以下のような状態になる可能性があります。

```text
WorkerA ---+
            |
            +--> RefCellA -> ExecutorA
            |
WorkerB ---+
```

WorkerAがExecutorAを可変借用している間に、WorkerBが同じRefCellを可変借用しようとすると、借用状態が衝突する可能性があります。

これによって、以下のエラーが発生すると考えられます。

```text
RefCell already borrowed
```

さらに、RefCellはスレッド間の同期を行う構造体ではありません。

そのため、異なるWorkerが同じRefCellにアクセスすると、単なるpanicだけでなく、データ競合による未定義動作につながる可能性があります。

# MicrosoftのFiber-safe TLS

今回の問題について調べると、MicrosoftのC/C++コンパイラ（MSVC）には、`/GT`というコンパイラオプションが存在することが分かりました。

https://learn.microsoft.com/en-us/cpp/build/reference/gt-support-fiber-safe-thread-local-storage

このオプションは、Fiber-safeなTLSアクセスをサポートするためのものです。
Fiberが別のスレッドで再開される可能性がある場合、TLS配列のアドレスが変化する可能性があります。

そのため、TLS配列のアドレスをキャッシュしたり、関数呼び出しをまたいで再利用したりする最適化を
考慮する必要があります。

`/GT`は、そのような最適化を抑制します。

つまり、Fiberのスレッド間移動とTLSの最適化の関係は、今回のゲームエンジンに限った問題ではありません。

ただし、`/GT`はMSVCのC/C++コンパイラのオプションであり、Rustにそのまま適用できるわけではありません。


# 原因の検証
TLSアドレスの再利用が実際に行われているかを確認するため、Releaseビルド後の`job_fiber_entry()`のアセンブリを確認します。特に、以下の`return_to_manager()`に着目します。

```rust
pub(crate) unsafe fn return_to_manager() {
    let manager = with_current_executor(|executor| {
        assert!(executor.current_fiber.is_some());
        executor.manager_fiber.as_ptr()
    });
    unsafe {
        SwitchToFiber(manager);
    }
}
```

`SwitchToFiber(target)`を呼ぶと、現在のOSスレッド上で実行するFiberが`target`に切り替わります。Fiberの初回実行時には`job_fiber_entry()`の先頭から実行され、2回目以降は前回の中断位置から実行が再開されます。`job_fiber_entry()`では、割り当てられたJobを実行し、Jobが完了すると`return_to_manager()`を呼び出してManager Fiberに実行を戻します。


`with_current_executor()`によるTLSへのアクセスと、`SwitchToFiber()`によるFiberの切り替え前後の処理を確認します。
可読性のため、アセンブリの一部を省略し、長いシンボル名を簡略化しています。

## TLSアドレスの取得

まず、`job_fiber_entry()`の開始部分を確認します。

```asm
job_fiber_entry:
    ...

    # 1. TLSインデックスを取得
    movl    _tls_index(%rip), %eax

    # 2. スレッドのTLS配列を取得
    movq    %gs:88, %rcx

    # 3. 対象モジュールのTLS領域を取得
    movq    (%rcx,%rax,8), %rax

    # 4. CURRENT_EXECUTORのアドレスを取得
    leaq    CURRENT_EXECUTOR@SECREL32(%rax), %rdi

    # 5. TLSの内部状態を取得
    movzbl  CURRENT_EXECUTOR@SECREL32+56(%rax), %eax

    # 6. TLSの内部状態に応じて分岐
    cmpl    $1, %eax
    je      .LBB28_4
    cmpl    $2, %eax
    jne     .LBB28_2

    ...
```

Windows x64では、各OSスレッドはスレッド固有の情報を格納するTEB (Thread Environment Block) を持ちます。TEBにはTLS Arrayへのポインタが格納されています。

TLS Arrayは、モジュール (EXEやDLL) ごとのTLS領域へのポインタを保持する配列です。

```text
OS ThreadA
    - TEB A
    - TLS Array A
        - [0]: モジュール0のTLS領域 (例: game.exe)
        - [1]: モジュール1のTLS領域 (例: physics.dll)
        - [2]: モジュール2のTLS領域 (例: audio.dll)

OS ThreadB
    - TEB B
    - TLS Array B
        - [0]: モジュール0のTLS領域 (例: game.exe)
        - [1]: モジュール1のTLS領域 (例: physics.dll)
        - [2]: モジュール2のTLS領域 (例: audio.dll)
```

各OSスレッドは独立したTEB、TLS Array、TLS領域を持ちます。

先ほどのアセンブリでは、以下の手順でTLS変数にアクセスしています。

* 1. TLSインデックスを取得
    - `_tls_index`から対象モジュールのTLSインデックスを取得する
    - `eax`に格納する
* 2. スレッドのTLS配列を取得
    - Windows x64では、GS Baseが現在のOSスレッドのTEBを指す
    - TEBの先頭から88bytes (0x58) の位置に格納されているTLS Arrayへのポインタを`rcx`に格納する
* 3. 対象モジュールのTLS領域を取得
    - TLS Arrayから対象モジュールのTLS領域へのポインタを取得する
    - `rax = *(rcx + rax * 8)`
* 4. CURRENT_EXECUTORのアドレスを取得
    - TLS領域の先頭アドレスにCURRENT_EXECUTOR用ストレージの相対オフセットを加える
    - `rdi = rax + CURRENT_EXECUTOR_OFFSET`
* 5. TLSの内部状態を取得
    - CURRENT_EXECUTOR用ストレージの先頭から56bytes先にある値を読み込む
* 6. TLSの内部状態に応じて分岐

ここで重要なのは、**CURRENT_EXECUTOR用ストレージのアドレスが`rdi`に格納されていること**です。

`rdi`はWindows x64の呼び出し規約における非揮発性レジスタであり、関数呼び出しの前後で値が保持されます。

## SwitchToFiber前後の処理

次に、`return_to_manager()`に対応するアセンブリを確認します。

```asm
.LBB28_143:
    # 1. RefCellの借用状態を確認
    cmpq    $0, (%rdi)

    # SwitchToFiber()の関数アドレスを取得
    movq    __imp_SwitchToFiber(%rip), %rdx
    leaq    TLS_DESTROY(%rip), %rsi

    jne     .LBB28_158

    # 2. RefCellの可変借用を開始
    movq    $-1, (%rdi)

    # 3. Executorとcurrent_fiberの状態確認
    movq    8(%rdi), %rax
    cmpq    $2, %rax
    je      .LBB28_160
    testq   %rax, %rax
    je      .LBB28_146

    # 4. Manager Fiberのポインタを取得
    movq    24(%rdi), %rcx

    # 5. RefCellの借用を終了
    movq    $0, (%rdi)

    # 6. SwitchToFiber(manager)
    callq   *%rdx

    # 7. TLSの内部状態を取得
    movzbl  56(%rdi), %eax
    cmpb    $1, %al
    jne     .LBB28_15
    jmp     .LBB28_18
```

このアセンブリでは、以下の処理が行われています。

* 1. RefCellが借用されていないことを確認
* 2. RefCellの借用状態を`-1`に設定し、可変借用を開始
* 3. Executorとcurrent_fiberの状態を確認
* 4. Manager Fiberのポインタを`rcx`に格納
* 5. RefCellの借用状態を`0`に戻し、可変借用を終了
* 6. `SwitchToFiber()`を呼び出し、Manager Fiberに切り替える
* 7. Job Fiberの再開後、TLSの内部状態を取得

まず、`SwitchToFiber()`を呼び出す前にRefCellの借用が終了していることが分かります。

次に、以下の2命令に着目します。

```asm
callq   *%rdx
movzbl  56(%rdi), %eax
```

`SwitchToFiber()`によってFiberの実行を中断した後、Fiberが再開されると、`movzbl`によってTLSの内部状態を取得しています。


`return_to_manager()`では、本来、`with_current_executor()`によって現在のOSスレッドのTLSからExecutorを取得します。

上記のReleaseビルド時のアセンブリを確認すると、`with_current_executor()`の処理がインライン展開され、TLSアドレスの再取得が省略されています。代わりに、以前取得したTLSアドレスを保持する`rdi`が再利用されています。Fiberが別のWorkerで再開される際には、非揮発性レジスタである`rdi`の値も復元されます。そのため、`rdi`が保持するTLSアドレスと、現在Fiberを実行しているOSスレッドのTLSアドレスが一致しなくなります。
これによって、現在のWorkerではなく、移動前のWorkerのExecutorを参照してしまう可能性があります。

## Fiberのスレッド間移動によるTLSアドレスの不一致
WorkerAでFiber1を実行し、WorkerBでFiber1を再開する場合を考えます。各WorkerのCURRENT_EXECUTOR用ストレージのアドレスを以下のように仮定します。

* WorkerA: `0x1000`
* WorkerB: `0x2000`

```
WorkerA                                WorkerB

ManagerFiberA                          ManagerFiberB
    |
    | SwitchToFiber(Fiber1)
    v
Fiber1
    |
    | job_fiber_entry()の先頭から実行
    | CURRENT_EXECUTORのアドレスを取得
    | rdi = 0x1000
    |
    | Jobが完了
    |
    | return_to_manager()
    | SwitchToFiber(ManagerFiberA)
    | 実行コンテキストを保存
    | (rdi = 0x1000)
    v
ManagerFiberA
    |
    | current_fiber = None
    | Fiber1を再利用可能にする
    |
    +-------- FreeFiberQueue ------------+
                                         |
                                         v
                                     ManagerFiberB
                                         |
                                         | SwitchToFiber(Fiber1)
                                         |
                                         | 実行コンテキストを復元
                                         | (rdi = 0x1000)
                                         v
                                     Fiber1 (再開)
                                         |
                                         | 前回のSwitchToFiber()の続きから実行
                                         |
                                         | movzbl 56(%rdi), %eax
                                         |
                                         | WorkerAのTLS領域を参照
                                         | rdi = 0x1000
                                         | (本来は0x2000)
```

`SwitchToFiber()`は、切り替え元のFiberの実行コンテキストを保存し、切り替え先のFiberの実行コンテキストを復元します。この実行コンテキストには、スタックポインタや非揮発性レジスタである`rdi`の値も含まれます。そのため、WorkerBがFiber1を再開すると、WorkerAで保存された`rdi = 0x1000`が復元されます。

本来、WorkerBのCURRENT_EXECUTOR用ストレージのアドレスである`0x2000`を取得する必要があります。しかし、最適化によってTLSアドレスの再取得が省略されているため、WorkerAのTLS領域を参照してしまいます。

つまり、**Fiberの実行コンテキストは正しく保存・復元されていますが、コンパイラが前提とする「関数の実行途中でOSスレッドが変化しない」という性質が、Fiberのスレッド間移動によって崩れています。**

## 検証結果
アセンブリから、以下のことが確認できました。

* TLSアドレスを非揮発性レジスタである`rdi`に格納している
* RefCellの借用を終了してから`SwitchToFiber()`を呼び出している
* `SwitchToFiber()`から戻った直後に、TLSアドレスを再取得せず`rdi`を再利用している

このことから、Fiberが別のWorkerで再開された場合、移動前のWorkerのTLS領域を参照してしまうと考えられます。

これによって、前述した2種類のエラーを説明できます。

* `current_fiber.is_some()`の失敗
    - 移動前のWorkerの`current_fiber`が既に`None`に設定されている
* `RefCell already borrowed`
    - 異なるWorkerが同じRefCellにアクセスし、借用状態が衝突する

以上のアセンブリは、TLSアドレスの再利用が今回のバグに関係しているという仮説を裏付けるものです。

# 解決方法

今回の問題に対処するため、`with_current_executor()`に`#[inline(never)]`を指定し、コンパイラによるインライン化を抑制します。

```rust
#[inline(never)]
fn with_current_executor<R>(
    f: impl FnOnce(&mut Executor) -> R
) -> R {
    CURRENT_EXECUTOR.with(|slot| {
        f(slot.borrow_mut().as_mut().expect("no current Executor"))
    })
}
```

これによって、TLSアドレスの取得処理を独立した関数の内部に閉じ込め、呼び出し元でのTLSアドレスの再利用を抑制します。

## 修正後のアセンブリ

修正後のReleaseビルド時のアセンブリを確認します。

```asm
.Ltmp190:
    # 1. with_current_executor()を呼び出す
    callq   with_current_executor
    nop

.Ltmp191:
    # 2. Manager Fiberのポインタを第1引数に設定
    movq    %rax, %rcx

    # 3. SwitchToFiber(manager)
    callq   *__imp_SwitchToFiber(%rip)

    # 4. Fiberの再開後、次の処理へ
    jmp     .LBB28_3
```

修正前は`with_current_executor()`の処理がインライン展開されていましたが、修正後は独立した関数として呼び出されていることが確認できます。

Windows x64の呼び出し規約では、ポインタの戻り値は`rax`に、第1引数は`rcx`に格納されます。

そのため、`with_current_executor()`が返したManager Fiberのポインタを`rax`から`rcx`にコピーし、`SwitchToFiber()`を呼び出しています。


# まとめ
* KaniVolcanoEngineでマルチスレッドとFiberによるジョブシステムを実装しました。Debugビルドでは見られなかったバグがReleaseビルドで出現しました。
* KaniVolcanoEngineでは、Fiberの実行コンテキストを保存・復元することで、Jobの一時停止や再開を可能にしています。また、中断したFiberを別のWorkerで再開することがあります。
* 今回確認したReleaseビルドのアセンブリでは、CURRENT_EXECUTOR用ストレージのアドレスが`rdi`レジスタに保持されていました。
* KaniVolcanoEngineでは、TLS領域にあるExecutorを介してFiberの切り替えを行っていました。
* Fiberを切り替える際、本来 (Debugビルド) なら毎回Executorを取得 (TLS領域へのアクセス) し、`SwitchToFiber()`しますが、ReleaseビルドだとExecutorの取得が省略されることがアセンブリから確認できました。
* これにより、Releaseビルド時は、あるスレッドのTLSからExecutorを取得しようとしても、別のスレッドのTLSを参照してしまうということが発生していました。
* インライン化を抑制することで対処しました。
* `#[inline(never)]`はインライン化を抑制するための属性であり、Fiberのスレッド間移動の安全性そのものを保証するものではありません。
