## はじめに
まずはじめに、間違ってることを書いてたらすみません。LLMに、自作ゲームエンジン「KaniVolcanoEngine」を使ってシューティングゲームを作ってもらったことについての記事です。
![](/images/KaniVolcano/shooting_game.png)
### ゲームエンジンとは
ゲームエンジンとは、ゲーム開発に必要な機能をまとめたソフトウェアです。一般的に、描画処理、物理演算、衝突判定、音声処理、入力管理など、さまざまなゲームで共通して必要となる機能を提供します。

「ゲームエンジン」という用語が広く使われるようになったのは1990年代です。特に、1993年にid Softwareが発売したFPS（First-Person Shooter）ゲーム『DOOM』は、ゲームエンジンという概念の普及に大きな影響を与えました。
DOOMの設計には、**描画システムや衝突判定などの基盤となる機能と、ゲーム固有のデータやルールを分離する**という特徴がありました。
この設計によって、開発者はゲームの基盤部分を一から作り直すことなく、ステージ、グラフィックス、キャラクターなどを変更することで、新しいゲームやコンテンツを制作できるようになりました。
その後、DOOMやQuakeなどの技術を基盤としたゲーム開発が広まり、ゲームエンジンのライセンス提供や、既存のゲームを改造するMOD（Modification）文化が発展しました。こうした流れは、ゲームエンジンを再利用可能なソフトウェア基盤として発展させる重要な契機となりました。

現在では、Unity、Unreal Engine、GameMakerなどの商用ゲームエンジンに加え、Godot EngineやBevy Engineといったオープンソースのゲームエンジンも広く利用されています。また、多くのゲーム開発企業が独自のゲームエンジンを開発し、自社タイトルの制作に活用しています。

このように、ゲームエンジンは長年にわたって進化を続け、**現代のゲーム開発を支える重要なソフトウェア基盤**となっています。

### なぜゲームエンジンを作るのか
なぜ企業や個人は、自らゲームエンジンを開発するのでしょうか。
企業の場合、その理由は比較的明確です。既存のゲームエンジンではカスタマイズに制約があったり、ライセンス料金が発生したりする場合があります。また、特定のゲームに最適化された機能が必要になることもあるでしょう。こうした理由から、独自のゲームエンジンを開発することには一定の合理性があります。

では、個人の場合はどうでしょうか。
単にゲームを作りたいのであれば、UnityやUnreal Engine、Godotなどを利用すればよいはずです。これらのエンジンには豊富な機能が備わっており、ドキュメントやチュートリアルも充実しています。わざわざ描画システムや物理演算、リソース管理などを一から実装する必要はありません。
それにもかかわらず、世の中には無数の個人製ゲームエンジンが存在します。その多くは誰からも注目されることなく、ひっそりと開発されています。
なぜなのでしょうか。
もちろん、理由は人それぞれでしょう。技術の習得、既存エンジンへの不満、独自の設計思想の実現など、さまざまな動機が考えられます。
しかし、個人的にはもっと単純な理由もあると思っています。

**「なんかかっこいいから」です。**

ゲームを開発していると、一定数、自分でゲームエンジンを作りたくなる人がいる気がします。おそらく。
彼らは、少しの承認欲求と大きな自己満足のために、膨大な時間をゲームエンジンの開発に費やします。ゲームを完成させることよりも、ゲームを動かす仕組みそのものを作ることに魅力を感じてしまうのです。
かくいう私も、その一人です。

特に現在は、LLMの存在によって個人開発のハードルが大きく下がっています。分からないことを調べたり、設計について相談したり、コードの実装を補助してもらったりしながら開発を進められます。新しい技術を学びながら、それを実際に動くものとして形にするまでの道のりが短くなり、達成感も得やすくなりました。
ゲームエンジンの自作は、プログラミングやコンピュータグラフィックス、ソフトウェア設計など、さまざまな技術を学ぶ良い機会にもなります。
そのため、個人的にはゲームエンジンの自作をおすすめします。
**ただし、ゲームを作りたい人にはおすすめしません。**

## KaniVolcanoEngineについて
自作ゲームエンジンにはKaniVolcanoEngineという名前を付けました。特徴は
* ECS(Entity Component System)の採用
* Vulkan APIを使用
* Rust製

です。GUIはなく、ユーザはコードベースでゲームを作成することになります。

### Vulkanとは
Khronos Groupが策定した低レベル・クロスプラットフォーム対応のグラフィックスAPIです。OpenGLのような他のグラフィックスAPIと比べて、GPUに詳細な情報を伝えることが出来る反面、プログラマが明示的に記述する部分が多くなります。Vulkanが提供する低レベルAPIにより、
* 描画命令をGPUに送る際のCPU負荷の低減による、オーバーヘッドの削減
* 明示的なマルチスレッド対応
* クロスプラットフォーム対応

というメリットが期待されます。しかし、Vulkanでは
* メモリ管理
* Swapchain (描画するイメージ) の作成・管理
* シェーダ/パイプライン構築
* DescriptorSet (シェーダーが使うリソースを指定するセット) の構築
* コマンド作成・送信
* 同期処理

を扱わなければなりません。開発者が毎度これらを明示するのは大変です。そこで、KaniVolcanoはこれらの低レベルな命令の集合を抽象化しAPIとして提供します。
例えば、
```rust
let polygon = context.spawn_polygon_3d(
    vec![
        vec3(-5.0, -0.4, -1.0),
        vec3(-5.0, -0.2, 0.0),
        vec3(-5.0, 0.5, -0.3),
        vec3(-5.0, 0.3, 0.2),
        vec3(-5.0, 0.0, 1.0),
        vec3(-5.0, -0.1, 1.2),
    ],
    vec3(0.0, 1.0, 0.0),
    1.0,
    Some("face"),
    PipelineKey::Lit3D,
)?;
```
のように書くことで、`Lit3D`というPipelineを選択し、環境光とスポットライトを反映するポリゴンを作成することができます。

### ECS (Entity Component System) とは
ECSとはEntity Component Systemの略です。
* Entity: 物体
* Component: 要素
* System: 法則

を別々に作成します。例えば、
```rust
// create new entity
let camera = context.spawn();

// grant entity a component (Transform)
context.add_component(camera, Transform::default());
// grant entity a component (Camera)
context.add_component(
    camera,
    Camera {
        target: vec3(-5.0, 0.0, 0.0),
        up: vec3(0.0,0.0,1.0),
        fov_y: 45.0,
        near: 0.1,
        far: 100.0,
        yaw: std::f32::consts::PI,
        pitch: 0.0,
    },
);

// enable a system (RotatorSystem)
context.add_update_system("rotator", RotatorSystem);
```
```rust
impl UpdateSystem for RotatorSystem {
    fn update(&mut self, context: &mut UpdateContext<'_>) -> Result<()> {
        let delta_time = context.delta_seconds();

        for (_, transform, rotator) in context.query2_mut::<Transform, Rotator>() {
            transform.rotate(rotator.speed * delta_time);
        }

        Ok(())
    }
}
```
このようにEntityを作成し、事前に定義した`Transform`と`Camera` ComponentをEntityに対して付与します。最後に`RotatorSystem`を適用することで、`RotatorSystem`をもつ、すべてのEntityに対して中身の実装を適用することが出来ます。  
ECSはOOP (オブジェクト指向) に対して、パフォーマンスが優れる傾向があります。この理由は、メモリ配置とキャッシュ効率です。OOPでは
```rust
struct Enemy {
    transform: Transform,
    health: Health,
    mesh: Mesh,
}
```
このように、1つのオブジェクトに様々なデータをまとめます。これらを更新する際は
```rust
for &mut enemy in enemies{
    enemy.transform.update();
}
```
みたいな感じになります。しかし各オブジェクトは
```
Enemy0: Transform Health AI Mesh
Enemy1: Transform Health AI Mesh
Enemy2: Transform Health AI Mesh
...
```
のように並んでいるため、CPUキャッシュには更新処理に使用しない`Health`や`Mesh`なども一緒に入りやすく、場所的局所性が低くなります。  
対してECSの場合、EntityはただのIDで、実体はComponentにあります。
```
Transform:
[T0][T1][T2][T3][T4]...

Health:
[H0][H1][H2][H3][H4]...
```
このように同じComponentが連続的に配置されているため
```rust
for transform in transforms {
    update(transform);
}
```
と順番に処理できます。連続したメモリの読み書きを可能にし、場所的局所性が高くなり、より効率的にキャッシュできます。

# 3Dシューティングゲーム開発仕様書

## 1. 概要

KaniVolcanoEngineを使用して、1人称視点（FPS）に近い3Dシューティングゲームを開発してください。

プレイヤーは3Dフィールド内を自由に移動し、周囲に配置されたターゲットを射撃して得点を獲得します。また、フィールド上の敵砲台からプレイヤーに向かって弾が飛んできます。プレイヤーは障害物を利用しながら攻撃を回避し、必要に応じて砲台を破壊できます。

**制限時間60秒以内に、できるだけ高いスコアを獲得すること**がゲームの目的です。HPが0になった場合はその時点でゲームオーバーです。

操作性、視認性、ゲームとしての完成度を重視してください。単に機能を実装するだけでなく、実際に遊んで楽しいゲームを目指してください。


## 2. ゲームシステム

### 2.1 プレイヤー

プレイヤーは以下の操作が可能です。

| 操作 | 入力 |
|---|---|
| 前進・後退 | W / S |
| 左右移動 | A / D |
| 視点操作 | マウス移動 |
| ジャンプ | Space |
| 射撃 | マウス左クリック |
| リロード | R |
| ゲーム開始・再挑戦 | Enter |
| 終了 | Esc |

- カメラは1人称視点に近い位置に配置してください。
- マウス操作により視線の方向を自由に変更できるようにしてください。
- プレイヤーの移動は視線の水平方向を基準としてください。
- ジャンプには重力を適用し、着地できるようにしてください。
- プレイヤーが地面や障害物を通り抜けないよう、必要な当たり判定を実装してください。
- 視点の上下回転には適切な角度制限を設けてください。

### 2.2 射撃システム

プレイヤーはカメラの向いている方向に弾を発射できます。

- 弾の最大装填数は5発です。
- 1回の射撃につき弾を1発消費します。
- 弾数が0の場合は射撃できません。
- Rキーでリロードでき、装填数が5発に回復します。
- リロードには適切な所要時間を設けてください。
- リロード中は射撃できないようにしてください。
- 射撃方向は画面中央の照準と一致させてください。
- 弾の移動、ターゲット・敵砲台との衝突、弾の消滅を実装してください。
- 弾には速度と最大生存時間を設けてください。
- プレイヤーの弾と敵の弾を区別し、敵弾が得点ターゲットを破壊したり、プレイヤーの弾がプレイヤー自身を傷つけたりしないようにしてください。

可能であれば、射撃時にマズルフラッシュ、発射音、着弾エフェクトを追加してください。

### 2.3 ターゲット

フィールド内に、得点が設定された複数のターゲットを配置してください。

ターゲットは立方体などの基本図形、または3Dモデルを使用して構いません。

- 各ターゲットには得点を設定してください。
- 得点はターゲット上、または近くにテキストとして表示してください。
- プレイヤーの弾がターゲットに命中すると、そのターゲットは破壊されます。
- 破壊したターゲットの得点がプレイヤーのスコアに加算されます。
- 同じターゲットから重複して得点を獲得できないようにしてください。
- ターゲットの得点によって色や大きさを変えるなど、視覚的な違いを設けてください。

ゲーム性を高めるため、必要に応じてターゲットの再出現、移動、高得点ターゲットなどを実装して構いません。

### 2.4 フィールド

3Dのゲームフィールドを構築してください。

以下の要素を配置してください。

- 地面
- フィールドの境界
- 大小さまざまな障害物
- 得点の異なる複数のターゲット
- 固定砲台（基本は4基）
- 必要に応じて装飾用のオブジェクト

障害物は単なる装飾ではなく、プレイヤーが回り込んだり、ジャンプで乗り越えたり、敵の射撃を遮ったりできるようにしてください。

ターゲットはプレイヤーの移動や視点操作を活用して狙う必要がある位置に配置してください。

砲台はフィールドの外周や高台など、攻撃の発生源を視認しやすい場所に配置してください。開始直後に全方位から集中砲火を浴びないよう、射線・遮蔽物・初期位置を調整してください。ゲームとして遊びやすいフィールド構造を設計してください。

### 2.5 スコアと制限時間

- ゲーム開始時のスコアは0点です。
- 制限時間は60秒です。
- ターゲット破壊時に対応する得点を加算してください。
- 敵砲台を破壊した場合も得点を加算してください（値はゲームバランスに合わせて設定）。
- 残り時間が0秒になったらゲームを終了してください。
- プレイヤーHPが0になった場合は制限時間内でもゲームオーバーにしてください。
- 終了後は射撃や移動によってスコアが変化しないようにしてください。
- 終了画面に最終スコアと終了理由（時間切れ／HP0）を表示してください。
- ゲーム終了後、Enterキーで再挑戦できるようにしてください。

ゲームは次の状態で管理することを推奨します。

1. Ready：開始待ち
2. Playing：ゲーム進行中
3. Result：結果表示（時間切れまたはHP0）

状態遷移に応じてUIや入力処理を切り替えてください。

### 2.6 敵砲台と敵弾【追加】

プレイヤーへ攻撃する敵として、**固定砲台を4基程度**配置してください。まずは固定砲台を確実に動作させ、ドローンなどの移動敵は必須としません。

- 砲台は視認可能な発射口を持ち、プレイヤーの位置に向かって弾を発射してください。
- 発射間隔は**2〜4秒程度**を初期値とし、遊びやすいように調整してください。各砲台の発射タイミングは適度にずらしてください。
- 弾速は**6〜10ワールド単位/秒程度**を初期候補とします。プレイヤーの移動速度・フィールドサイズに合わせ、目で見て回避できる速さにしてください。
- 敵弾はプレイヤーに命中するとダメージを与え、障害物に当たると消滅してください。
- 敵弾は最大生存時間または射程の制限で消滅させ、無限に蓄積しないようにしてください。
- 砲台からプレイヤーまでの射線が障害物で遮られる場合は、可能であれば発射を控えるか、弾が遮蔽物に当たるようにしてください。障害物を貫通してはいけません。
- 砲台は破壊可能とし、必要な命中回数（例：2〜3発）を設定してください。
- 砲台を破壊した場合、その砲台は攻撃を停止し、得点を一度だけ加算してください。
- 砲台が破壊されても既に飛んでいる弾の扱いが一貫するようにしてください（例：発射済みの弾は残る）。
- 発射口の発光や発射前の短い予告、弾道の色分けなど、攻撃を認識しやすい演出を優先してください。

初期状態では複雑な追尾弾や瞬間着弾する攻撃を避け、**発射時点のプレイヤー位置を狙う直進弾**を基本としてください。敵弾とプレイヤー弾は明確に異なる色・形で表示してください。

### 2.7 HP・被弾・ゲームオーバー【追加】

- プレイヤーの初期HPおよび最大HPを**100**にしてください。
- 敵弾1発あたりのダメージは**10**を初期値としてください。
- 被弾直後は**0.7秒程度の無敵時間**を設け、重なった弾による瞬間的な連続ダメージを防いでください。
- 無敵時間中も衝突した敵弾は適切に処理し、同じ弾から複数回ダメージを受けないようにしてください。
- HPの値は0〜最大HPの範囲に収めてください。
- 被弾時は画面の一時的な赤色フラッシュ、効果音、HUD変化などで明確に通知してください。
- HPが0になったら直ちにゲームを終了し、敵の攻撃・スコア更新などを停止してください。
- 再挑戦時はHP、残弾数、砲台、敵弾、ターゲット、スコア、残り時間、各種タイマーを初期状態に戻してください。

## 3. UI / HUD

画面上にゲームの情報を分かりやすく表示してください。

### 3.1 スコア表示

- 画面右上に現在のスコアを表示してください。
- ターゲットや砲台の破壊時には即座に更新してください。
- 得点獲得時に加算された点数を一時的に表示するなど、演出を追加して構いません。

### 3.2 弾薬表示

### 3.3 残り時間

- 残り時間が少なくなったら色を変えるなど、視覚的に警告してください。

### 3.4 照準

- 実際の射撃方向と照準の位置が一致するようにしてください。

### 3.5 開始画面・結果画面

開始画面にはゲームタイトル、操作方法、開始方法を表示してください。

結果画面には最終スコア、終了理由、再挑戦方法を表示してください。

UI全体は画面サイズやアスペクト比を考慮して配置してください。

### 3.6 HP表示・危険通知【追加】

- HPを常時表示してください（例：`HP  80 / 100` とゲージ）。配置はスコアや弾薬表示と重ならない位置にしてください。
- 低HP時には色を変えるなど、危険な状態が直感的に分かるようにしてください。
- 被弾時の演出は視界を完全に塞がず、照準や敵弾の視認性を維持してください。
- 可能であれば被弾方向を示すインジケータを追加して構いません。

## 4. ビジュアル・演出

- 視認性を損なわない配色にしてください。
- ターゲット・砲台の破壊時に視覚的なフィードバックを追加してください。

- 射撃、命中、リロード、被弾などに効果音を追加して構いません。

外部アセットが必要な場合は、利用可能なファイルやエンジンのロード機能を確認してください。

外部アセットが用意されていない場合でも、基本図形や既存機能を組み合わせて成立するゲームにしてください。

## 5. 実装要件

### 5.1 ファイル構成

ゲームの中心となるSceneを、以下のファイルに実装してください。

`shooting_game_scene.rs`

必要に応じて、`component`や`system`ディレクトリ内に新しいComponentやSystemを自由に追加して構いません。

ゲームロジックをすべてScene内に詰め込むのではなく、責務に応じて適切に分割してください。既存の実装がある場合は、そのファイル構成と責務分担を尊重してください。

### 5.2 KaniVolcanoEngineの利用

**既存のKaniVolcanoEngineの設計やAPIを十分に確認してから実装してください。**

- Scene、Component、Systemなどの既存の仕組みを優先して使用してください。
- ECSを活用してエンティティの状態と処理を管理してください。
- Transform、Camera、MeshRendererなど、既存のComponentを可能な限り再利用してください。
- 既存の描画、入力、テキスト、音声、アセット管理機能を活用してください。
- エンジンに存在しないAPIを推測で使用しないでください。
- ゲーム固有のロジックは、可能な限りエンジン本体を変更せずに実装してください。
- エンジン本体に変更が必要な場合は、既存設計との整合性と影響範囲を考慮してください。

### 5.3 GPUリソース管理

**同じ形状やモデルを繰り返し使用する場合は、GPUリソースを再利用してください。**

- 同一のMeshやTextureをエンティティごとに重複してGPUへ確保しないでください。
- Meshの共有とTransformによる位置・回転・スケールの変更を基本としてください。
- ゲームの毎フレーム処理で不要なGPUリソース生成を行わないでください。
- 弾やターゲットなど、頻繁に生成・消滅するオブジェクトには、必要に応じてオブジェクトプーリングを検討してください。
- 敵弾・砲台についても共有Mesh/Materialなどを活用してください。
- 不要になったリソースはエンジンの管理方式に従って適切に扱ってください。

### 5.4 JobSystemによる並列化

必要に応じて、KaniVolcanoEngineのJobSystemを利用してください。

ただし、並列化によるオーバーヘッドが処理時間を上回らないようにしてください。

- 小規模な処理は原則として逐次実行してください。
- 十分な数の独立した処理が存在する場合のみ並列化を検討してください。
- 並列処理中のデータ競合を防止してください。
- ECSのComponentに対する参照や可変アクセスの安全性を維持してください。
- JobSystemの使用そのものを目的にしないでください。

### 5.5 当たり判定

少なくとも以下の当たり判定を実装してください。

- プレイヤーと地面
- プレイヤーと障害物
- プレイヤー弾と得点ターゲット
- プレイヤー弾と敵砲台【追加】
- 敵弾とプレイヤー【追加】
- 敵弾と障害物【追加】
- 必要に応じてプレイヤー弾と障害物

高速な弾が対象をすり抜けないように、移動区間に沿った衝突判定（例：線分と球／AABBの交差判定）などを検討してください。衝突が複数候補と成立する場合は、弾の移動方向で最初に当たる対象を優先してください。

物理演算ライブラリを新たに導入する必要はありません。ゲーム規模に適したシンプルな実装を優先してください。

### 5.6 更新処理と状態の整合性【追加】

- 移動速度、発射間隔、無敵時間、リロード時間、60秒タイマーなどは経過時間に基づいて更新し、フレームレートに依存しないようにしてください。
- プレイヤー弾・敵弾は所有者または陣営を区別して処理してください。
- 同一フレームに複数の弾が命中しても、破壊済み砲台やターゲットへの二重加点を防止してください。
- ゲーム終了後・再挑戦後に古い弾や古いタイマーの状態が残らないようにしてください。
- 画面外や時間切れの弾は確実に回収または非アクティブ化してください。

## 6. 開発方針
