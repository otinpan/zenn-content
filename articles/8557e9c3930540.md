## はじめに
### Crackmes.oneとは
Crackmeとは、リバースエンジニアリングの技術を練習するために作られたプログラムのことです。一般的なCrackmeには、パスワードやシリアルキーの入力を求める認証処理が組み込まれています。例えば、実行すると次のように表示されます。
```
Enter password: ********
Wrong password!
```
解析者はソースコードを見ずに、実行ファイルを解析して正しいパスワードや認証アルゴリズムを特定します。  
[Crackmes.one](https://crackmes.one/)とは、CrackmeをダウンロードできるWebサイトです。

## 問題
今回はパスワード解析の問題を解いていきます。[rootaccess2011's CrackMe with password](https://crackmes.one/crackme/697635e09bf7b8997653a6d8)からダウンロードします。  
フォルダを展開して、実行ファイルを開くと
```
Enter Password:
```
と表示されるので何か入力しましょう。

![](/images/rootaccess/console.png)

正解パスワード以外は拒否されます。

## 解法
各ツールのインストール方法等は[ここ](https://zenn.dev/otinpan/articles/5e7fff41ed645d)を参考にしてください。

### 事前準備
まずは、ファイル情報をDetect It Easy (DIE)で取得します。
![](/images/rootaccess/DIE.png)

* Protector: Oreans CodeVirtualizer
* Protector: Themida/Winlicense (3.XX)
* (Heur) Protector: Generic
* (Heur) Packer: Generic

これらの情報からパッキングされていることが分かります。そのため、Ghidraのような静的解析ツールでの解析は難しそうです。（この後一応確かめます）

### 静的解析
一応Ghidraで逆コンパイルできるか確かめます。
entry point -> `FUN_1405af34f()` を見てみます。`FUN_14038e058()`は初期化処理です。
![](/images/rootaccess/entry.png)
![](/images/rootaccess/ghidra_main.png)

やはり、Ghidraで逆コンパイルしたものから、パスワードを解析するのは厳しそうです。

### 動的解析
次はデバッガを使用して、パスワードの解析を試みます。x64dbgで実行ファイルを選択し開きます。次に、パスワード入力後に現れる"Access denied"を文字列検索してみましょう。
![](/images/rootaccess/denied.png)

```
000000014000186C | E8 7FFBFFFF              | call <rootaccess2011.check_input>       |
0000000140001871 | 48:8D0D F8690000         | lea rcx,qword ptr ds:[140008270]        | rcx:NtQueryInformationThread+14, 0000000140008270:"Access granted."
0000000140001878 | 85C0                     | test eax,eax                            |
000000014000187A | 75 07                    | jne rootaccess2011.140001883            |
000000014000187C | 48:8D0D FD690000         | lea rcx,qword ptr ds:[140008280]        | rcx:NtQueryInformationThread+14, 0000000140008280:"Access denied."
0000000140001883 | FF15 C7680000            | call qword ptr ds:[<puts>]              |
0000000140001889 | 48:8D0D 006A0000         | lea rcx,qword ptr ds:[140008290]        | rcx:NtQueryInformationThread+14, 0000000140008290:"\nPress Enter to exit..."
```
をみると、`<rootaccess2011.check_input>` (これは私が付けた名前) で`eax`レジスタの値が書き換えられます。
```
test eax,eax
```
から、`eax`が0なら"Access denied"、それ以外なら"Access granted"が表示されることが分かります。ということは、`<rootaccess2011.check_input>`を見ればよさそうです。

はい！0x1400013F0番地から0x140001771番地まであります！！(はー、長げ)
![](/images/rootaccess/checkinput.png)
![](/images/rootaccess/checkinput2.png)

これは頭から読むのは無理ですね。ではどこを見ればよいのでしょうか。先ほど、`eax`レジスタが0以外なら"Access granted"と表示されることが分かりました。では、この関数の後ろから`eax`レジスタの値を変えている部分を探しましょう。最後の何行かです。

`<rootaccess2011.last check>`の結果`eax`が0なら`rootaccess2011. 140001752` (`eax`の変更はしていない) を呼びリターンします。そうでない場合は、
```
lea rdx,qword ptr ss:[rsp+40]
mov rcx,rbx
call <JMP.&strcmp>
...
mov eax,ecx
```
を経由して、同じようにリターンします。どうやら、この`strcmp`がかなり怪しいです。`strcmp`では`rcx`と`rdx`を比較するので、ここでは`rbx`と`ss:[rsp+40]`を比較しています。では、ブレークポイントを置いてみてみましょう。
```
<je rootaccess2011. last check>
```
に置きましたが、ここに到達せずに終了してしまいました。何が駄目なのでしょうか。
次に疑うべきは、
* 文字数判定
* 不正文字

にひっかかったことです。仕方ないので、この関数の先頭である0x1400013F0番地から見ていきましょう。

ここら辺まで見るとわかるでしょうか。

```
call <JMP.&strlen>
cmp eax,E
```

では、正に文字列の長さを求め、`0xE`と比較しています！文字列の長さは14であることが推測できます。  
では入力に14文字の文字列 (`0123456789abcd`) を与え、再度ブレークポイントを置き、実行します。  
さきほどの文字列比較を復習すると、
```
0000000140001736 | 74 18                    | je rootaccess2011.140001750             |
0000000140001738 | 48:8D5424 40             | lea rdx,qword ptr ss:[rsp+40]           |
000000014000173D | 48:8BCB                  | mov rcx,rbx                             | rbx:"0123456789abcd"
0000000140001740 | E8 A90D0000              | call <JMP.&strcmp>                      |
```
なので、`rbx`と`ss:[rsp+40]`の文字列を比較しています。
ブレークポイントを置いて、レジスタの値を確認すると`rbx`は入力した文字列なので、`ss:[rsp+40]`に正解文字列が入っていることが推測できます。
![](/images/rootaccess/breakpoint.png)

`ss:[rsp+40]`を見ます。
```
000000000015ED80  65636361746F6F72  
000000000015ED88  0000373333317373  
```
でした。x64dbgはリトルエンディアンなので
```
72 6F 6F 74 61 63 63 65
73 73 31 33 33 37 00 00
```
となり、これをASCIIにすると
```
rootaccess1337
```
となります。  

再度実行して、パスワードに入力してみると通るはずです！！

(ちなみに、関数の前半部分は、入力文字列の置換 -> ハッシュ値計算 -> ハッシュ値使ってなんかやる -> ... みたいなことをしてるっぽい)

## まとめ
今回は、DIEでファイル情報を取得した結果、パッキングされていることが分かりました。また、Ghidraでの静的解析が困難なことが確認できました。そこで、x64dbgで  
文字列検索 -> 条件確認 (`eax!=0`) -> 入力文字数の特定 -> ブレークポイント置いてメモリ読む -> ASCII変換 -> 正解文字列特定  
ということをやりました。  
今回の問題を通して、問題の範囲を特定する力が養われたと思ってくれたらうれしいです。
